# Размещение на VPS Ubuntu 24.04

Подготовленная схема для `ioo.megaev.ru` → `185.200.179.49`:

```
Браузер ──HTTPS──> Nginx/Caddy ──127.0.0.1:8787──> Node.js ──HTTPS + ключ──> OpenAI
```

Node.js отдаёт сайт и API `/api/ai`. По выбранной схеме сайт открыт для всех,
без логина посетителя. API-ключ задаётся только в окружении службы.
На VPS интерфейс ввода ключа и внешнего прокси скрыт. Даже прежний сохранённый
ключ браузера не используется. Политика CSP `connect-src 'self'` разрешает
браузеру обращаться только к серверу сайта.

## 1. Сначала проверить существующего агента и доступ к OpenAI

До установки или перезапуска служб собрать состояние:

```bash
sudo ss -lntp
systemctl list-units --type=service --state=running --no-pager
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Ports}}'
node --version
free -h
```

Если Docker или Node отсутствуют, соответствующая команда сообщит об этом.
Вывод команд не содержит значений переменных окружения. Не публиковать `.env`,
API-ключи, пароль SSH или полную конфигурацию уже работающего агента.

После загрузки проекта на VPS проверить реальный запрос к OpenAI:

```bash
cd /opt/tko-ioo
/opt/tko-node/bin/node server/check-openai.js
```

Скрипт запросит ключ скрытым вводом и отправит короткий запрос модели.
При 403 сначала разобраться с доступом аккаунта/сервера к OpenAI; смена места
хранения ключа не исправляет отказ провайдера. Ключ в чат присылать не нужно.

## 2. Изоляция приложения

Схема файлов:

| Путь | Назначение |
| --- | --- |
| `/opt/tko-ioo` | отдельная копия проекта |
| `/opt/tko-node` | отдельный Node.js 22+; системный Node агента не меняется |
| `/etc/tko-ioo.env` | ключ, модель и лимиты; `root:root`, режим `600` |
| `/var/lib/tko-ioo/usage.json` | суточный счётчик запросов; без документов и ключей |
| `tko-ioo.service` | отдельная служба под пользователем `tko` |
| `127.0.0.1:8787` | внутренний порт; проверить, что он свободен |

Backend не требует production npm-зависимостей. Если порт 8787 занят, выбрать
свободный и одновременно изменить `PORT` и адрес upstream в Nginx/Caddy.
Не заменять файлы, пользователя, Node.js или службы существующего агента.

Пример установки файлов **после инвентаризации сервера**:

```bash
sudo useradd --system --home-dir /opt/tko-ioo --shell /usr/sbin/nologin tko
sudo git clone https://github.com/KAMegaev/tko-ioo.git /opt/tko-ioo
sudo install -o root -g root -m 600 /opt/tko-ioo/server/.env.example /etc/tko-ioo.env
sudo nano /etc/tko-ioo.env
```

Задать `OPENAI_API_KEY`. Оставить `TKO_PUBLIC_ACCESS=true` для открытого сайта
и `PUBLIC_ORIGIN=https://ioo.megaev.ru`. Начальный общий лимит — 50 обращений
к ИИ в день по московскому времени; `MAX_DAILY_REQUESTS` можно изменить.
Счётчик сохраняется между перезапусками, при ошибке записи обращения к ИИ
приостанавливаются. Запросы к провайдеру с ошибками тоже расходуют этот лимит.
Для закрытого режима можно установить `TKO_PUBLIC_ACCESS=false` и задать
`TKO_USERNAME` и `TKO_PASSWORD` (не менее 12 символов).
Node.js установить отдельно в `/opt/tko-node`, после проверки архитектуры
`uname -m`; не использовать команды обновления системного Node.js агента.

```bash
sudo install -m 644 /opt/tko-ioo/server/deploy/tko-ioo.service /etc/systemd/system/tko-ioo.service
sudo systemctl daemon-reload
sudo systemctl enable --now tko-ioo
curl --fail http://127.0.0.1:8787/healthz
```

Ожидаемый ответ: `{"status":"ok"}`. Убедиться, что приложение слушает только
`127.0.0.1`, а работающий агент продолжает отвечать.

## 3. Домен и HTTPS

В DNS-зоне `megaev.ru` создать отдельную A-запись:

```
ioo    A    185.200.179.49
```

Проверить A- и AAAA-записи: у нового поддомена не должно быть старого IPv6,
ведущего на другой сервер. Записи корня `megaev.ru` менять не требуется.

Веб-сервер выбрать по владельцу портов 80/443:

- **Nginx уже работает:** добавить отдельный virtual host из `deploy/nginx-http.conf`.
  Создать `/var/www/letsencrypt`, проверить `nginx -t` и плавно перечитать конфигурацию.
  Выпустить сертификат только для нового поддомена:

  ```bash
  sudo certbot certonly --webroot -w /var/www/letsencrypt -d ioo.megaev.ru
  ```

  Затем добавить `deploy/nginx-https.conf`, снова `nginx -t` и reload.
  HTTP перенаправляется на HTTPS; документы передаются по HTTPS.
- **Caddy уже работает:** добавить блок из `deploy/Caddyfile.snippet`; сертификат
  обслужит Caddy. Nginx параллельно на занятые порты не устанавливать.
- **Порты обслуживает другой агент/контейнер:** сначала определить его схему
  маршрутизации. Не останавливать процесс и не менять правила вслепую.
- **Порты свободны:** выбрать Nginx или Caddy и настроить только новый сайт.

## 4. Проверка перед использованием

Открыть `https://ioo.megaev.ru`. В открытом режиме пароль не запрашивается.
Надпись подключения должна сообщать «OpenAI через сервер сайта». Поля API-ключа
в браузере быть не должно. В Network обращения идут только к домену сайта,
AI-запросы — `POST /api/ai`. Проверить PDF, DOCX и расчёт с реестром.

Backend обрабатывает файлы в памяти и не создаёт хранилище документов.
В шаблоне Nginx отключено буферизование тела запроса на диск.
К OpenAI отправляются полный документ нормативов либо образец реестра,
а не весь реестр. Ограничения: 16 МБ на документ, 24 МБ на запрос, 2 одновременных
обращения к ИИ и 20 запросов в минуту с IP. Общий суточный предел, модель
и параллелизм меняются в `.env`. Одна загрузка комплекта может включать
извлечение нормативов и разметку реестра — это два обращения к ИИ.

Состояние приложения: `systemctl status tko-ioo`; журнал: `journalctl -u tko-ioo`.
Backend не пишет тела документов или значения ключей в журнал. HTTP-ошибки
провайдера возвращаются с сообщением для диагностики и без серверного ключа.

После проверки сайта настроить автоматический деплой GitHub → VPS по
[инструкции](deploy/README.md). Workflow Pages удалён; уже опубликованный старый
сайт снять через Settings → Pages → Unpublish site. Основной адрес — `https://ioo.megaev.ru`.
